# Первый живой запуск Barrymore с Ornith

Цель этого прогона — не подобрать окончательные параметры модели, а проверить
целый продуктовый путь: Barrymore поднимается, разговаривает через локальную
модель, сохраняет непрерывность, показывает обычную разговорную поверхность и
при необходимости может безопасно привлекать внешний персонал.

## Модель

Для первого прогона используется:

`Ornith-1.5-9B-AD-Q5_K-Q4_K.gguf`

Ожидаемый dev-путь:

`data/local_models/Ornith-1.5-9B-AD-Q5_K-Q4_K.gguf`

Это не обязательная модель Barrymore. Runtime и личность Бэрримора не зависят
от конкретных весов; Ornith сейчас только кандидат на лёгкую постоянно живущую
разговорную модель.

## Перед запуском

```sh
make ornith-ready
```

Проверка сообщает:

- найден ли точный GGUF-файл;
- виден ли обычный `llama-server` в ожидаемых местах;
- доступен ли `bubblewrap` для изоляции внешнего персонала.

Отсутствие `bubblewrap` не мешает самому Barrymore и локальной модели. Оно
запрещает запуск персонала в режимах, где Barrymore обещает kernel-level
изоляцию, в том числе при обязательном proxy.

## Запуск

```sh
make run
```

Dev-профиль первого прогона:

- context: 8192;
- CPU threads: 14;
- GPU layers: 99 (попытка отдать модели максимум доступного GPU);
- интерфейс: `http://127.0.0.1:7717`;
- разрешённый по умолчанию dev workspace root: `$HOME/git`.

8K выбран намеренно как безопасная стартовая точка для 8 ГБ VRAM. Если модель
стабильно помещается и скорость устраивает, окно можно увеличивать уже по
измерениям. Долгая память Barrymore хранится runtime'ом и не требует держать
всю историю в KV-cache.

## Proxy внешнего персонала

Откройте `Настройки → Сеть персонала`.

Например:

`http://127.0.0.1:12334`

Эта настройка не применяется к самому Barrymore и его `llama-server`.

Если proxy задан, внешний worker получает только loopback bridge внутри
отдельного network namespace. Недоступный proxy означает отказ запуска, а не
попытку выйти напрямую.

Изменение или отключение proxy — глобальное немедленное решение. Barrymore
останавливает уже работающий внешний персонал, проверяет, что старые процессы
умерли, закрывает старые relay и только затем публикует новую политику. После
успешного ответа интерфейса не должно быть смеси старого proxy, нового proxy и
прямого маршрута.

## Что проверить руками

1. Barrymore открывается сразу, даже если локальная модель ещё грузится.
2. В обычной навигации видны `Разговор` и `Настройки`, а внутренние инспекторы
   доступны только после включения технического режима.
3. После ответа Ornith разговор остаётся центральной поверхностью.
4. После reload Стол закрыт; накопленные решения не пропали и видны по
   счётчику.
5. Несколько простых реплик не заставляют модель выдумывать состояние машины.
6. Повторный разговор о прежнем деле узнаёт контекст без необходимости вручную
   выбирать внутреннюю нить.
7. Proxy можно включить/сменить/выключить из настроек без перезапуска Barrymore.
8. При недоступном proxy внешний worker не стартует.

## Что записать по итогам

Для настройки Ornith нужны факты, а не ощущения:

- время загрузки модели;
- VRAM/RAM после загрузки;
- скорость первого токена и обычного ответа;
- насколько устойчив structured output Barrymore;
- хватает ли 8K контекста;
- качество узнавания прежнего контекста;
- были ли ошибки `llama-server`/chat template/JSON schema;
- насколько часто для обычных фраз действительно хочется позвать более
  сильного внешнего исполнителя.

После этого уже имеет смысл менять quant, context, offload или саму resident
модель.
