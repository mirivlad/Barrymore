# ADR 0023: прокси относится к персоналу, а не к самому Бэрримору

Статус: принято

Дата: 2026-08-20

## Контекст

Внешние исполнители — Codex, Claude Code, OpenCode, Hermes и подключаемые CLI —
могут обращаться к сетевым провайдерам. На некоторых машинах такой доступ
должен идти через настроенный владельцем прокси.

При этом внешний персонал является ускорителем, а не условием существования
Бэрримора. Runtime, память, собственные умения, наблюдения и локальная модель
должны продолжать работать без внешних агентов и без их сетевого маршрута.

Глобальные `HTTP_PROXY`/`ALL_PROXY` у процесса Бэрримора дали бы неверную
границу: через прокси неожиданно пошли бы собственные HTTP-запросы runtime и
локальный `llama-server`, хотя владелец настраивал транспорт именно для
персонала.

## Решение

### 1. Прокси — настройка запуска внешних работников

Бэрримор хранит необязательную настройку `worker_proxy`.

Если она пуста, поведение запусков не меняется.

Если она задана, runner добавляет внешнему worker-процессу стандартные
переменные окружения:

- `HTTP_PROXY` и `http_proxy`;
- `HTTPS_PROXY` и `https_proxy`;
- `ALL_PROXY` и `all_proxy`;
- `NO_PROXY` и `no_proxy` для loopback.

Одна настройка действует на встроенные и будущие adapter'ы одинаково. Adapter
не должен знать, каким способом владелец маршрутизирует сеть.

### 2. Сам Бэрримор не наследует этот маршрут как HTTP policy

`worker_proxy` не превращается в `HTTP_PROXY` процесса `barrymored`.
Локальный `llama-server` также не получает эти стандартные proxy variables от
настройки персонала.

Внутри процесса хранится только приватная для Barrymore переменная-маркер,
которую понимает runner. В стандартные proxy variables она превращается только
в момент создания процесса исполнителя.

Таким образом внешний персонал можно полностью отключить или оставить без
сети, не меняя работоспособность дворецкого.

### 3. Поддерживаемые адреса

На первом срезе принимаются прокси со схемами:

- `http://`;
- `https://`;
- `socks5://`;
- `socks5h://`.

Адрес обязан содержать host. Query, fragment и нетривиальный path запрещены.
Учётные данные внутри URL на первом срезе запрещены: они попали бы в окружение
каждого worker-процесса и усложнили бы модель секретов. Если понадобится
авторизованный прокси, его учётные данные должны получить отдельную безопасную
модель, а не быть случайным свойством строки URL.

### 4. Loopback всегда обходится

Runner задаёт `NO_PROXY=localhost,127.0.0.1,::1`. Исполнитель не должен пытаться
ходить через внешний прокси к локальному callback/server только потому, что у
него включена сеть.

### 5. Настройка владельца сильнее adapter'а

Если adapter сам передал proxy variable, явно настроенный `worker_proxy`
переопределяет её. Иначе один worker мог бы молча обойти политику маршрутизации,
в то время как другой её соблюдает.

## Следствия

1. Не требуется добавлять proxy code в Codex/Hermes/OpenCode adapter'ы.
2. Подключённый позднее незнакомый CLI автоматически получает тот же маршрут.
3. Отсутствие прокси не считается ошибкой или деградацией.
4. Настройка может отображаться в UI как настройка персонала, а не сети самого
   Бэрримора.
5. Секреты прокси пока не поддерживаются намеренно; это честнее, чем хранить их
   в `settings.json` и child environment без отдельного threat model.

## Не делаем этим решением

- не проксируем локальную модель;
- не заставляем Бэрримора зависеть от доступности прокси;
- не поднимаем собственный VPN/туннель;
- не пытаемся перехватывать сеть на уровне ядра вместо стандартного механизма
  CLI-приложений;
- не обещаем, что произвольный worker уважает proxy variables: это наблюдаемая
  возможность, которую можно подтвердить реальным запуском.
