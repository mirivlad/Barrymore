# ADR 0023: прокси персонала — fail-closed граница

Статус: принято

Дата: 2026-08-20

## Контекст

Внешние исполнители — Codex, Claude Code, OpenCode, Hermes и подключаемые CLI —
могут обращаться к сетевым провайдерам. На некоторых машинах такой доступ
должен идти через настроенный владельцем прокси.

При этом внешний персонал является ускорителем, а не условием существования
Бэрримора. Runtime, память, собственные умения, наблюдения и локальная модель
должны продолжать работать без внешних агентов и без их сетевого маршрута.

Одних `HTTP_PROXY`/`HTTPS_PROXY` недостаточно. Они объясняют добросовестному
клиенту, куда идти, но не запрещают произвольному CLI открыть прямой socket.
Требование владельца строже: если прокси указан, внешний worker либо идёт через
него, либо не выходит в сеть вообще.

## Решение

### 1. Прокси относится только к внешнему персоналу

Бэрримор хранит необязательную настройку `worker_proxy`.

Если она пуста, сетевое поведение worker'ов определяется их sandbox-plan как и
раньше.

Если она задана и конкретному worker нужна сеть, runner включает proxy-only
режим. Сам `barrymored`, его HTTP API, собственные умения и локальный
`llama-server` эту настройку как свой `HTTP_PROXY` не получают.

Внутри процесса хранится приватная переменная `BARRYMORE_WORKER_PROXY`; она не
является общей сетевой политикой процесса.

### 2. Proxy-only — это отдельный network namespace

Worker запускается только через `bubblewrap --unshare-net`.

В таком namespace нет маршрута к хосту или интернету; остаётся только loopback.
Поэтому worker, который игнорирует proxy variables и делает прямой TCP/UDP
connect, физически не получает обычного сетевого выхода.

Если `bubblewrap` недоступен, запуск worker с обязательным прокси запрещается.
Тихого fallback на обычную сеть нет.

Стандартные host runtime-каталоги `/run`, `/tmp` и `/var/tmp` скрываются своими
tmpfs, чтобы DBus, ssh-agent, Docker и подобные host-сокеты не превращались в
случайный обходной канал.

### 3. Встроенный bridge внутри sandbox

Для proxy-only запуска runner оборачивает worker приватным режимом того же
бинарника `barrymored`.

Bridge слушает только `127.0.0.1:17717` внутри worker namespace. Worker получает
стандартные переменные:

- `HTTP_PROXY` / `http_proxy`;
- `HTTPS_PROXY` / `https_proxy`;
- `ALL_PROXY` / `all_proxy`.

Но в них указан только loopback bridge. Настоящий адрес прокси worker не
получает.

Для SOCKS bridge объявляется как `socks5h://`: имя целевого узла передаётся
SOCKS-серверу и не требует DNS из изолированного namespace.

### 4. Встроенный host relay

Bridge соединяется с host-side частью Barrymore через Unix socket в личном
cache-каталоге владельца. Relay реализован внутри Barrymore на Go; отдельный
`socat` или другой runtime-helper не требуется.

Host relay открывает наружу только соединение к самому настроенному proxy.
Содержимое HTTP CONNECT / SOCKS-запроса передаётся как данные: Barrymore не
делает прямых соединений к целевым адресам вместо worker'а.

Для `https://` proxy TLS до настоящего proxy устанавливает host relay и
проверяет сертификат по реальному hostname. Worker внутри namespace при этом
может использовать обычный `http://127.0.0.1:17717`: открытый локальный участок
никуда за пределы его изолированного loopback не выходит.

### 5. Недоступный прокси запрещает запуск

Перед exec внешнего worker host relay делает короткий preflight соединения к
настроенному proxy.

Если proxy недоступен, запуск завершается ошибкой до старта worker. Нельзя
интерпретировать недоступность proxy как разрешение попробовать прямую сеть.

Если proxy исчез уже во время работы, bridge закрывает неудавшееся соединение.
Fallback отсутствует; worker остаётся в network namespace без прямого egress.

### 6. Поддерживаемые адреса

Принимаются:

- `http://`;
- `https://`;
- `socks5://`;
- `socks5h://`.

Адрес обязан содержать host. Если порт не указан, relay использует стандартные
80, 443 или 1080 соответственно. Query, fragment и нетривиальный path
запрещены.

Учётные данные внутри URL пока запрещены: они требуют отдельной модели секретов
и не должны случайно оказаться строкой в `settings.json` или окружении процесса.

### 7. Настройка владельца сильнее adapter'а

Если adapter сам передал proxy variables, runner заменяет их своим loopback
route. Adapter не может молча выбрать другой proxy или отключить маршрут
владельца через окружение.

### 8. `worker_proxy` — одна глобальная политика текущего персонала

После того как владелец нажал «Применить», у него должен существовать один
однозначный ответ на вопрос: через что сейчас выходит в сеть внешний персонал.
Смесь старого proxy, нового proxy и direct route недопустима.

Поэтому изменение `worker_proxy` применяется в таком порядке:

1. валидируется новый адрес;
2. все текущие внешние worker-процессы останавливаются с причиной
   «изменена сетевая политика персонала»;
3. runtime проверяет, что старые процессы действительно умерли; если нет —
   изменение отменяется;
4. старые host relay закрываются и их Unix sockets удаляются;
5. effective policy и сохранённая настройка переключаются на новое значение;
6. только после этого новые worker-процессы могут стартовать с новой политикой.

Отключение proxy — такое же изменение политики. Уже работающий персонал не
продолжает пользоваться старым proxy: он останавливается, старый relay
уничтожается, а новые запуски получают обычную сеть.

Горячо переносить живой CLI между маршрутами не пытаемся. Это создало бы
непроверяемое промежуточное состояние и сделало интерфейс настроек лживым.

Отдельные socket paths для upstream всё равно используются как защита от
случайной подмены маршрута внутри одного запуска и как непрозрачные
идентификаторы, не раскрывающие адрес proxy в имени файла.

## Следствия

1. Не требуется proxy-код в Codex/Hermes/OpenCode/Claude adapter'ах.
2. Подключённый позднее незнакомый CLI автоматически получает ту же границу.
3. Отсутствие внешних агентов или proxy не мешает самому Бэрримору работать.
4. В proxy-only режиме `bubblewrap` становится обязательной runtime-зависимостью
   именно для персонала, потому что гарантию даёт kernel namespace, а не договор
   с CLI.
5. Реальный endpoint proxy остаётся на host-side; worker видит только loopback.
6. `socat` не добавляется: обе половины relay принадлежат бинарнику Barrymore.
7. Изменение proxy немедленно прекращает текущие внешние запуски; скрытого
   «старого маршрута до конца поручения» нет.
8. Если хотя бы один старый worker не удалось остановить, новый proxy не
   публикуется как действующий.

## Не делаем этим решением

- не проксируем локальную модель;
- не заставляем Бэрримора зависеть от доступности proxy, пока он работает сам;
- не поднимаем VPN;
- не выдаём worker обычный host network namespace при включённом proxy;
- не считаем proxy variables защитой сами по себе — они только интерфейс к
  loopback bridge, а запрет обхода обеспечивает network namespace.
